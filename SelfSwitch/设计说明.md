# SelfSwitch 设计说明（v1.1 · 实现思路 / 关键技术点 / 已知限制）

> 目标：Windows 11 上，让「全屏的 Chrome」和「全屏的目标 EXE」之间一键来回切换。
> 本工具**不启动、不关闭任何程序**，只切换**已经打开**的窗口。

## 二、显示方式策略（v1.7 起 Chrome 与目标 EXE 共用一套）

两边各自独立配置，共 8 种，实现在 `ToggleService.Activate()` 里统一分发（`ApplyDisplayMode` 语义）：

| 显示方式 | 实现 | 是否覆盖任务栏 |
|---|---|---|
| `SendF11` | 聚焦 → 判断是否已铺满 → 未铺满才发 F11 → 320ms 后回检 → 仍不铺满则回退覆盖任务栏 | 是（真全屏） |
| `CoverTaskbar` | 直接 `SetWindowPos(HWND_TOPMOST, 铺满整屏)` | 是 |
| `Maximize` | `ShowWindow(SW_SHOWMAXIMIZED)` | 否 |
| `MaximizeCoverTaskbar` | 先 `SW_SHOWMAXIMIZED`，再铺满整屏 + 置顶 | 是 |
| `Windowed` | `ShowWindow(SW_RESTORE)`，恢复成普通窗口（保留自身尺寸位置） | 否 |
| `CustomRect` | 先 `SW_RESTORE`，再 `SetWindowPos` 到 `x,y,w,h`（支持百分比） | 否（除非区域就是整屏） |
| `KeepCurrent` | 只 `ForceForeground`，完全不碰窗口大小位置 | 否 |
| `SendAltEnter` | 同 F11 流程，发 Alt+Enter | 取决于程序 |

### 几个关键设计点

- **发键类（F11 / Alt+Enter）必须先判断"是否已铺满"**：这两个键是开关式的，无脑发会把已经全屏的窗口**切出去**。判断用 `GetWindowRect` vs `MonitorFromWindow + GetMonitorInfo(rcMonitor)`，容差 4px。
  Chrome 的 F11 真全屏窗口矩形与显示器矩形**完全相等**（误差 0）；而 Win10/11 的**最大化**窗口会比工作区外扩约 8px（> 4px 容差）→ 被判"未全屏"→ 发 F11，正是期望行为。
- **发键后回检 + 自动回退**：320ms 后重新比对，仍没铺满就说明程序不支持该快捷键，自动改用 `SetWindowPos` 覆盖任务栏——保证"点了有反应"。
- **非置顶类模式先取消置顶**：`Maximize` / `Windowed` / `CustomRect` / `KeepCurrent` 执行前先 `HWND_NOTOPMOST`，否则上一次用"覆盖任务栏"留下的 TOPMOST 会一直压着别的窗口。
- **自定义区域支持百分比**：`RectSpec.TryParse` 把 `x,y,w,h` 四项分别解析（带 `%` 的按显示器宽高的百分比算，否则按像素），默认值 `0,0,50%,100%` / `50%,0,50%,100%` 直接构成**左右分屏**。配置非法时 `Normalize()` 回落默认值并写 WARN；运行时再校验一次，非法则本次回退为最大化。
- **日志保留旧关键字**：发键前后的实测值仍写成 `F11 判断(Chrome)` / `F11 发送后(Chrome)` 这类格式，既有测试工装不用改。

### 覆盖任务栏的原理

`SetWindowPos(hwnd, HWND_TOPMOST, 显示器左, 显示器上, 宽, 高, SWP_SHOWWINDOW | SWP_NOOWNERZORDER)` —— 用精确几何尺寸铺满整屏，**比 Maximize 更可靠**（最大化窗口仍会避开任务栏）。先 `HWND_TOPMOST` 再 `SetForegroundWindow`，保证盖住任务栏并且拿到焦点。
显示器矩形取自 `MonitorFromWindow + GetMonitorInfo(rcMonitor)`：单屏环境就是主屏 (0,0)-(W,H)；多屏时铺满窗口当前所在的那块屏，不会把窗口硬拽到主屏。

## 三、其余实现要点

### 1. 窗口识别：为什么必须用进程完整路径

- Chrome 和业务程序都可能被改名、可能有多个窗口，**靠窗口标题识别不可靠**。
- 过滤链（顺序执行，越早越省性能）：
  1. `IsWindowVisible` 为真；
  2. `GetWindowTextLength > 0`（Chrome 有大量无标题的隐藏窗口，在这一关被拦掉）；
  3. `GetWindow(hwnd, GW_OWNER) == 0`（排除对话框 / 弹出窗口）；
  4. 扩展样式不含 `WS_EX_TOOLWINDOW`；
  5. `GetWindowThreadProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `QueryFullProcessImageName` 取完整路径；
  6. `PathHelper.Equals(进程路径, 配置路径)`（忽略大小写、统一斜杠、去引号）。
  7. 可选：`WindowTitleKeyword` 非空时，窗口标题还必须包含它（忽略大小写）；路径命中但标题都不符 → 视为未找到并写日志，不会误切。
- **多窗口怎么选**：`EnumWindows` 按 Z 序（前 → 后）回调，第一个命中即"Z 序最前/最近激活"的窗口。同一次枚举用 `Dictionary<pid,path>` 缓存进程路径。
- **不要用"尺寸接近屏幕"做过滤条件**：Chrome 刚打开还没全屏时尺寸就不是全屏尺寸，加了这条会直接找不到窗口。

### 2. 切换方向判断（最容易出错的地方）

- **严格模式（默认开启）**：前台是 Chrome → 切目标 EXE；前台是目标 EXE → 切 Chrome；**前台是其它任何程序 → 静默忽略**（不切换、不弹提示，只在 `app.log` 写一行）。
- **关闭严格模式后**：前台是其它程序时，看 `_lastForegroundPath`（上次真正的前台程序）决定方向，无记录则默认切 Chrome。

**坑**：悬浮按钮自己也是窗口，用户一点它，它就成了前台窗口，方向判断直接失效（永远只会切到 Chrome）。**解决**（两重保险）：
1. 悬浮窗加 `WS_EX_NOACTIVATE`（+ XAML `ShowActivated=False`、`Focusable=False`）——点击它**不抢焦点**；
2. `ToggleService._lastForegroundPath` 兜底记录（严格模式关闭时使用）。

> 注意严格模式的一个副作用：**托盘图标双击 / 点击托盘菜单打开配置窗口后**，前台可能变成小工具自己，这时点悬浮按钮不会有反应——这是设计如此，把焦点切回 Chrome 或目标程序再点即可。

### 3. 强制把窗口切到前台

`SetForegroundWindow` 会被前台锁定策略拦截。处理顺序：
1. `AttachThreadInput(当前线程, 前台窗口线程)` → `BringWindowToTop` + `SetForegroundWindow`；
2. 仍失败则模拟按下/抬起 **Alt 键**解除锁定后重试；
3. 最后用 `GetForegroundWindow() == hwnd` **实证校验**，失败写日志；
4. 无论成败都 `AttachThreadInput(..., false)` 断开，避免线程输入队列粘连。

### 4. 悬浮按钮

- XAML：`WindowStyle=None` + `AllowsTransparency=True` + `Background=Transparent` + `ShowInTaskbar=False` + `Topmost=True` + `SizeToContent=WidthAndHeight`。
- 定位：主屏**工作区**（`Screen.PrimaryScreen.WorkingArea`，已排除任务栏）为参考系，按 `Anchor`（四角可选的锚点）加减 `OffsetX` / `OffsetY`；用 `VisualTreeHelper.GetDpi` 换算 DIP，避免 125%/150% 缩放下偏移。
  > 默认锚点右下 + 偏移 12 → 按钮正好浮在任务栏上方 12px，不会被任务栏挡住。
  > **想让按钮压在任务栏上**：把 X/Y 偏移设成**负值**（例如 -20）即可——此时位置夹取范围会从"工作区"放宽到"整屏"，不会被"保护"住（这是 v1.5 修的问题 F：v1.4 及以前负值会被 `Normalize()` 夹成 0，根本压不过去）。
  > 换锚点 / 调偏移也是**避开输入法状态条、系统通知横幅**这类第三方置顶浮窗的手段（见 4.3）。
- 半透明：`Window.Opacity` 默认 0.75，鼠标进入赋 1.0、离开赋回配置值——**无任何动画**。
- 右键菜单：打开配置 / 退出程序；左键 = 切换；**不注册任何全局热键**。
- `WS_EX_NOACTIVATE` 的副作用：系统不会把它自动压在全屏窗口之上，所以切换完成后 400ms×3 次 `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` 重新置顶。
- **按钮文字随前台窗口变化（v1.3）**：文字表达"点下去会切到哪里"，三套文字分别对应「前台是 Chrome」「前台是目标程序」「其它」，都在配置界面可改。刷新机制见下面 三.5。

### 4.1 按钮文字实时跟随前台（v1.3）

- 两个机制叠加，既即时又不漏：
  1. `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)` —— 前台窗口一变立刻回调（out-of-context 不注入任何进程，回调在装钩子的 UI 线程进来，再 `Dispatcher.BeginInvoke` 排一次队）；
  2. `DispatcherTimer` 1 秒兜底轮询 —— 防极少数事件丢失。
- **开销控制**：只有"前台窗口句柄"变化时才去 `OpenProcess + QueryFullProcessImageName` 解析进程路径；句柄没变直接返回。所以 1 秒轮询几乎零成本。
- 只在**分类发生变化**时触发 `StateChanged`（不会每帧刷文字，也不会有动画）。
- 两个必须注意的实现细节：
  - 钩子回调委托必须用静态字段**保持强引用**，否则被 GC 回收后回调会崩；
  - 配置里路径改了要调 `Invalidate()` 清掉句柄缓存并强制重判，否则会一直沿用旧分类。
- 文字变化会改变按钮宽度（`SizeToContent=WidthAndHeight`），按钮是**右下角锚定**的，宽度变化只会让左边缘移动，右边缘不动；`SizeChanged` 事件里会重算位置。

### 4.2 其它程序在前台时自动隐藏（v1.4）

- 与严格模式同一套判断：前台分类为 `Other` 且 `HideButtonWhenOther=true` → `Visibility = Hidden`；回到 `Chrome` / `Target` → 恢复 `Visible` 并立刻 `PositionWindow()` + 置顶。
- 用 `Visibility.Hidden` 而**不是** `Collapsed`：Hidden 会保留布局，`ActualWidth/ActualHeight` 仍然有效，重新显示时不需要等一次布局就能算准位置（不会闪一下）。
- **必须做的防护**：`BringToFront()` 里加了 `if (Visibility != Visibility.Visible) return;`。因为 `Win32.EnsureTopmost` 带 `SWP_SHOWWINDOW`，如果不管住它，切换完成后那 3 次"重新置顶"会把已经隐藏的按钮**强行弹出来**。
- 隐藏不代表"失去控制入口"：托盘图标不受影响（右键=配置/退出，双击=切换）。
- 它同时改变了 v1.3 的行为：原来前台是其它程序时显示 `—`，现在默认直接藏起来；`ButtonTextOther` 只在关掉自动隐藏时才有意义。

### 4.3 v1.5：按测试报告逐条修复

| 报告问题 | 根因 | 修复 |
|---|---|---|
| **A（P1）启动时前台已是 Chrome/目标 → 按钮不出现** | `Window_Loaded` 里 `ApplyConfig()` 先跑，用 `Current` 的初始值 `Other` 把按钮判成隐藏；随后 `Invalidate()` 算出的正确分类因为"StateChanged 还没人订阅"被丢弃，而 `Start()` 里的 `Refresh()` 又因句柄未变短路 → 可见性再也没被同步过 | 调整初始化顺序：**先订阅 → 再 Start() → 最后 ApplyConfig()**；并把"文字 + 可见性"收敛成唯一入口 `SyncButtonAppearance()`，两处调用不会再有分歧 |
| **B（P2）未知枚举值 → 整份配置被丢弃** | `JsonStringEnumConverter` 在反序列化阶段就抛 `JsonException`，被外层 catch 整体兜住；`Normalize()` 里"枚举越界回默认"永远走不到 | 新增 `LenientEnumConverter<T>`：无法识别/越界的取值**只回落该字段默认值**并写 WARN，其余字段照常加载；同时把修正后的配置**回写磁盘**，避免每次启动重复报错 |
| **C（P2）按钮被输入法状态条/通知横幅盖住 → 点不动** | 输入法是注入到前台进程内的窗口，前台一变就被一起抬到最上层；工具只在"显示按钮时"和"切换完成后 400ms×3"置顶，**前台变化这个时刻没有重新置顶** | `OnForegroundStateChanged` 里补一次 `BringToFront()`（内部保留"隐藏时不置顶"的防护，不会被 `SWP_SHOWWINDOW` 弹出来） |
| **C 的根治手段（P2）** | 单一边距只能沿对角线调，躲不开浮窗 | 位置配置升级为 **锚点（四角）+ 独立 OffsetX/OffsetY**，支持负值（可主动压到任务栏上）；旧字段 `EdgeMargin` 自动代入，老配置不用改 |
| **D（P3）连点防重入实际不生效** | WPF 鼠标消息在 UI 线程忙时是**排队**而不是丢弃，且 `Monitor` 对同线程可重入 | `Toggle()` 增加**时间节流**：距上次切换完成 < 400ms 的点击直接丢弃并写 WARN，行为与文档一致 |
| **E（P3）偏移 0 时按钮压住任务栏 1px** | `Math.Round` + DPI 换算取整外溢 | 改用 `Math.Floor` 并对工作区做越界夹取（多留 1 DIP）——宁可偏上偏左 1px，也不压任务栏 |
| **F（P3）README 关于边距/任务栏的描述与实现相反** | 文档写错 | 文档已改写：压任务栏要**用负偏移**，且 v1.5 起负偏移真的生效了 |
| **G（P3）损坏配置移走后不回写默认值** | `Load()` 的 catch 只 return，不落盘 | catch 分支补 `def.Save(path)`，日志文案也改成中性描述（"配置文件不存在，已生成默认配置"） |
| **H（P3）关闭严格模式与自动隐藏互斥** | 非严格模式下"其它程序"时按钮其实有用，却被藏起来点不到 | 自动隐藏改为**仅在严格模式开启时生效**（严格模式关掉后自动忽略隐藏），配置界面 tooltip 说明 |
| **I（观察项）受保护进程可能刷 WARN** | 每次前台变化都取进程路径，失败即写 WARN | 同一 PID 的取路径失败 **1 分钟只写一条** WARN |
| **I（观察项）** | explorer 重启后托盘图标是否恢复（未验证） | WinForms `NotifyIcon` 内部已处理 `TaskbarCreated` 自动重加，未加代码；建议现场目视确认一次 |

### 4.4 v1.6：现场联调暴露的三个问题

现场反馈"绑定之后无法进行切换"，日志定位到根因是**配置的目标路径写错**（配置 `D:\Doubao\Doubao.exe`，实际运行的是 `D:\Doubao\app\Doubao.exe`）。围绕这一类故障做了三处加固：

| 问题 | 说明 | 修复 |
|---|---|---|
| **① 路径写错无法自查** | 路径不对 → 永远"未找到目标 EXE 窗口"，但用户不知道错在哪 | 新增**自动诊断**：找不到窗口时，去枚举所有同名进程的可见窗口，把真实路径直接写进托盘气泡 + `app.log`（"疑似路径写错：配置=... ，实际找到同名窗口在 ..."）。彻底解决"不知道该填什么" |
| **② 配置界面靠手抄路径** | 用户去任务管理器翻路径，容易抄错一层目录 | 两个路径框各加一个「**取当前窗口**」按钮：一键填入"最近一次出现在前台的窗口（本工具自己不算）"的进程完整路径。实现上用 `ForegroundWatcher.LastForeignPath` 记录值——因为点按钮本身会让配置窗口变成前台，实时取只会取到工具自己 |
| **③ 系统壳窗口干扰** | 日志里 4 分钟内 10 次"新通知"（`Windows.UI.Core.CoreWindow`）和任务栏（`Shell_TrayWnd`）抢前台：每次都把按钮藏起来，严格模式还会误判成"其它程序"而静默忽略点击 | 新增 `IgnoreShellWindows`（默认开）：通知横幅 / 任务栏 / 操作中心 / 托盘旋出窗抢前台时，**不改变按钮状态、也不参与切换方向判断**，改用"最近一次真实程序窗口"。命中时日志写"前台是系统壳窗口（通知/任务栏），保持按钮状态不变" |
| **④ 节流把失败也算了** | v1.5 的 400ms 节流对"找不到窗口"的失败点击也生效，用户越急越点不动（日志里连续 10+ 条节流告警就是证据） | 节流只在**真的切换成功**后计时；失败/被忽略的点击不占节流窗口，可以立刻重试 |

### 4.5 v1.7：浏览器侧也做成"显示方式可选"

需求："给浏览器也加一下各种类型——最大化、窗口化这些；其他你判断能不能加。"

做法：**把原本只给目标 EXE 用的 4 种全屏方式，升级成 Chrome 与目标 EXE 共用的一套 8 种显示方式**
（`WindowDisplayMode` 单一枚举，`ToggleService.Activate()` 统一分发，不再有 ActivateChrome / ActivateTarget 两个分支）。

判断后新增的 4 种（原 4 种保留）：

| 新增 | 为什么加 |
|---|---|
| `Windowed` 窗口化 | 用户明确要的。恢复成普通窗口，保留自身尺寸位置——适合"我要看标题栏/随时拖动"的场景 |
| `CustomRect` 自定义区域 | 窗口化的自然延伸：不给尺寸的窗口化没意义（窗口可能小得像针眼或跑到屏幕外）。**支持百分比**，默认值直接构成左右分屏，顺手解决"两个程序各占半屏"的用法 |
| `KeepCurrent` 保持当前状态 | 有些程序自己管窗口尺寸（如浏览器套壳客户端），工具碰它反而出问题。这个模式只切前台 |
| `SendAltEnter` 给 Chrome 也开放 | 本身是通用快捷键（Chromium 系、播放器、游戏都认），放开没有坏处 |

**没有加**的两个（判断后放弃）：
- **"是否置顶"做成独立开关** —— `CoverTaskbar` 已经覆盖这个需求；单独置顶容易让窗口压住所有程序、反而切不回来，弊大于利。
- **"最小化目标窗口"** —— 语义上不是"显示方式"，需要的话用 `KeepCurrent` + 手动最小化即可。

兼容性：枚举按名称序列化，历史取值 `SendF11`/`CoverTaskbar`/`Maximize`/`MaximizeCoverTaskbar`/`SendAltEnter` 名字全部保留 → **旧 config.json 直接能读**；配置界面下拉项改成"由数组映射"，不再依赖枚举数值顺序（这是这次最容易踩的坑）。

### 4.6 v1.8：悬浮按钮可自由拖动摆放

需求："UI 可以全屏随意自行 UI 位置" —— 悬浮按钮要能用鼠标拖到屏幕任意位置并记住。

| 实现点 | 做法 |
|---|---|
| 拖动 | `MouseLeftButtonDown` 记下鼠标屏幕坐标与窗口左上角 → `CaptureMouse()`；`MouseMove` 按位移同步 `Left/Top` |
| 与"点击"区分 | 位移**超过 4 DIP 阈值**才算拖动；没超阈值时松手仍按"点一下切换"处理（不会因为手抖吃掉点击） |
| 拖动范围 | 夹在**整屏**内（不是工作区）——用户明确要随意放，允许压在任务栏上 |
| 松手 | 写回配置 `FreePosition=true` + `FreeX/FreeY`（**存物理像素**，换缩放比例后位置更真实）并落盘；拖动只是挪位置，**不触发切换** |
| 复位 | 配置界面「按钮位置」下新增一行提示 + 「复位到锚点」按钮：清空记忆、回到锚点+偏移计算的位置 |
| 定位优先级 | `PositionWindow()`：`FreePosition` 有效 → 用记忆坐标（夹在屏幕内）；否则 → 锚点 + 偏移 |
| 细节 | 拖动期间不改透明度（`MouseLeave` 在拖动中直接 return）；`PointToScreen` 拿到的是 DIP 屏幕坐标，与 WPF 的 `Left/Top` 同一坐标系，不会因 150% 缩放错位 |

**注意**：一旦拖动过，`Anchor`/`OffsetX`/`OffsetY` 就不再生效（配置界面里会显示当前拖动坐标并提示）。想回到按锚点摆放，点「复位到锚点」即可。

### 4.7 v1.9：快速切换全局快捷键

需求："设置一个快捷键进行快速切换"。（注：最初需求里写的是"不需要全局热键"，本次按新要求放开。）

| 项目 | 做法 |
|---|---|
| 机制 | `RegisterHotKey` 注册到悬浮窗的 HWND（`MOD_NOREPEAT` 关掉自动重复），`HwndSource.AddHook` 收 `WM_HOTKEY` |
| 默认 | **开启**，组合键 `Ctrl+Alt+S` |
| 与点击按钮的关系 | **完全等效**：走同一个 `ToggleService.Toggle()`，一样受严格模式、防重入、400ms 节流约束（不是"强制切换"后门） |
| 隐藏状态下可用 | 按钮被"其它程序自动隐藏"藏起来时，窗口句柄仍存在，快捷键照样工作（但严格模式下前台不是两者时会静默忽略） |
| 改键 | 配置界面点进框直接按组合键，`PreviewKeyDown` 里把 `ModifierKeys + Key` 转成规范字符串（如 `Ctrl+Alt+S`）；按 Backspace 清空 |
| 合法性 | 必须带 Ctrl/Alt/Shift/Win 中至少一个，或单独一个 F1~F24（`HotkeySpec.TryParse` 统一校验，配置界面、`Normalize()`、注册前各校验一次） |
| 失败处理 | 注册失败（多为被别的程序占用）→ 写 WARN + 托盘气泡告知错误码，不影响程序其它功能；退出时 `UnregisterHotKey` 释放 |
| 兼容 | `Ctrl+Alt+S` 被占用时改一个即可，例如 `Ctrl+Shift+F9` |

**踩到的坑（记录一下）**：`App.OnExit` 里写 `MainWindow.Instance` 编译不过——`App` 继承自 `Application`，而 `Application.MainWindow` 是个同名属性，成员访问上下文里 `MainWindow` 解析成了那个属性。必须写成 `SelfSwitch.MainWindow.Instance` 才能指到自己的类型。同类坑：WPF `Key` 枚举**不支持比较运算符**（`key >= Key.A` 编译错误），要先转 `int`。

### 4.8 v1.9.1：修一个自己引入的真 bug + 加版本可辨识

**① 拖动后松手会误触发一次切换（v1.8 引入的真 bug）**

```csharp
// v1.8（错）：EndDrag() 内部把 _dragMoved 清成 false，
// 所以后面这句判断永远不成立 → 拖完松手也会切一次
EndDrag();
if (_dragMoved) return;
```
改成让 `EndDrag()` 返回"这次是不是拖动"，用返回值判断；顺带在拖动结束时写一行 `拖动结束，本次不触发切换` 方便对数：

```csharp
bool wasDrag = EndDrag();
if (wasDrag) { Logger.Info("拖动结束，本次不触发切换"); return; }
```

**教训**：跨方法的"标志位"被清空后仍在外层读取，是典型的顺序陷阱。凡是"读标志 → 调清标志的方法 → 再读标志"的写法，都要让被调方**返回结果**，别依赖字段状态。

**② 版本号可辨识（这次的误会根源）**

用户反馈"点击和 UI 位置变化好像没实现"，实际上都实现了，只是**跑的是旧 EXE**（多副本 + 快捷方式指向旧文件）。为了让这类误会一眼可破：

- 启动日志第一行带上版本：`=== SelfSwitch 启动 === 版本=1.9.1 exe=…`；
- 托盘图标悬停提示带版本：`SelfSwitch 窗口切换工具 v1.9.1（双击=切换）`；
- 验收清单最前面加了"3 秒确认版本"对照表。

### 4.9 v1.10.0：现场日志定位到"点击被吃掉"的真根因

用户上传现场 `app.log`（579 行），逐行比对后定位到一个**能完整解释"点按钮没反应"**的机制：

```
21:40:00.453 前台窗口类别变化: Other | title="SelfSwitch"      ← 点按钮的瞬间，按钮窗口自己成了前台
21:40:00.453 前台是其它程序 → 悬浮按钮已自动隐藏               ← 立刻被"自动隐藏"藏掉
21:40:00.476 前台窗口类别变化: Chrome → 悬浮按钮已显示         ← 23ms 后又显示出来
（同一动作在 21:40:00 / :07 / :19 / :26 重复了 4 次，日志里都没有 查找结果:）
```

**因果链**：点按钮 → 窗口被激活成前台（说明 `WS_EX_NOACTIVATE` 在这一刻没起作用）→ 前台分类变 `Other` → 命中"其它程序自动隐藏" → 窗口被隐藏 → **鼠标松开事件再也收不到** → 这次点击彻底丢失；窗口随后因前台回到 Chrome 而又显示出来，用户看到的就是"按钮闪了一下、什么都没发生"。

四处修复：

| # | 修复 | 说明 |
|---|---|---|
| 1 | **交互期间禁止改显隐** | `ApplyVisibility()` 开头判断 `_mouseDown \|\| _dragging` → 直接 return。只要鼠标还按在按钮上，任何"其它程序"判定都不能把它藏起来（这是根因修复） |
| 2 | **自己进程视为"透明"** | 前台是本工具自身窗口（配置窗口 / 悬浮按钮）时，`ForegroundWatcher` **不改变**按钮状态与文字；`ToggleService` 也不把它当"其它程序"，改用"最近一次真实程序窗口"判方向。顺带修掉"点完配置窗口再按快捷键被严格模式吞掉"（现场日志 21:39:41 那条） |
| 3 | **`WS_EX_NOACTIVATE` 加校验与复查** | 启动时（`SourceInitialized`）和窗口加载后（`Loaded`）各设置并**读回校验**一次，日志写 `悬浮按钮无激活样式(WS_EX_NOACTIVATE)=已生效 [Loaded]`。以前只是设置、不校验，样式位若被 WPF 覆盖也无从发现 |
| 4 | **「取当前窗口」拒绝系统进程** | 现场日志出现过两次把 `C:\Windows\explorer.exe` 填进目标路径（21:04:17、21:04:53）。现在遇到 explorer/系统目录进程会弹提示让用户先把目标程序点到最前面 |

另外为了诊断"点击有没有送达按钮"，在 `MouseLeftButtonDown` 加了一行 `悬浮按钮：鼠标按下（接下来按位移判定是「点击」还是「拖动」）`——以后点一下没反应，看日志有没有这行就能立刻区分"点击没送到"还是"送到了但被规则拦下"。

### 4.10 v1.11.0：位置调整挪进配置界面，按钮只负责"单击=切换"

用户要求：**"移动在设置里面进行，点击之后可以进行拖动；单击 UI 进行切换，这样不影响单击切换"**。

也就是说：v1.8 那种"在按钮上直接拖动"会和"单击切换"互相干扰（要靠 4 DIP 阈值区分，还得防"拖动后误触发切换"）。干脆把两件事彻底分开：

| 能力 | 现在在哪 |
|---|---|
| **单击悬浮按钮** | 只做一件事：**切换窗口**（不再有任何拖动判定，100% 不会吃掉点击） |
| **调整位置** | 配置界面 →「按钮位置」→「**调整位置**」按钮 |

### 位置调整模式的完整流程

```
配置界面点「调整位置」
  ↓ 配置窗口隐藏（App.BeginPlacement）
  ↓ 悬浮按钮进入跟随模式：30ms 轮询 GetCursorPos，按钮中心跟着鼠标走
  ↓ 用户移到想要的位置
  ↓ 单击一下 → ConfirmPlacement()：写 FreePosition=true + FreeX/FreeY（物理像素）→ 落盘 → 托盘气泡告知
  ↓ 配置窗口自动显示回来，位置提示刷新为"当前位置：调整后的位置 (X=…, Y=…)"

（中途按 Esc → CancelPlacement()：按钮回到调整前的位置，配置窗口显示回来）
```

### 几个实现要点

- **跟随不靠鼠标事件**：窗口如果没被激活就收不到 `MouseMove`，所以用 `GetCursorPos` 轮询（30ms）——不依赖焦点、不依赖捕获，稳。
- **确认用 `GetAsyncKeyState(VK_LBUTTON)`** 轮询，同样不依赖窗口被激活；`Esc` 同理。
- **进入后 500ms 内不认确认**：否则"点『调整位置』按钮"的那一下左键会被立刻当成确认，位置直接定死在配置窗口附近。
- **位置调整期间禁止自动隐藏**（`ApplyVisibility` 里 `_mouseDown || _placing` 直接 return）——沿用 v1.10.0 修的根因，保证这次点击不会丢。
- 保留「复位到锚点」与「锚点 + X/Y 偏移」：想精确摆放还是用数字，想快点就用「调整位置」。
- 拖动相关的字段（`FreePosition/FreeX/FreeY`）沿用，不新增配置项，老配置直接兼容。

### 4.11 v1.11.1：配置界面按钮看不见（布局坑）

**③ UI 布局坑：横向 StackPanel + 长提示文字把按钮挤出窗口（v1.11.1 修）**

配置界面「按钮位置」第二行原本是 `[长提示文字] [调整位置] [复位到锚点]` —— 提示文字约 60 个汉字（≈780px），
而窗口宽 700px、内容区只有约 470px，**横向 StackPanel 不会换行**，于是两个按钮被挤到窗口右边界之外，用户根本看不到。

修复：
- 按钮放到左边、提示文字放右边并加 `TextWrapping="Wrap"` + `MaxWidth="360"`；
- 配置窗口宽度 700 → 880（内容区约 648px），把其它几行也一并放宽（严格模式/忽略壳窗口/自启 的长文案、快捷键行的提示）；
- 快捷键行提示从"点框内直接按组合键；按 Backspace 清空"缩成"点框内按组合键；Backspace 清空"。

**通用规则**：WPF 横向 `StackPanel` 里的 `TextBlock` **不会自动换行也永远不会缩**，长文案会直接把后面的控件推出可视区。
凡是"提示文字 + 按钮"同行，要么按钮放前面，要么给 TextBlock 加 `MaxWidth` + `TextWrapping`。

### 5. 配置与落盘位置

- 全部可配置项集中在 `AppConfig`，`System.Text.Json` 序列化，**枚举以字符串保存**，中文不转义，允许注释与尾逗号。
- 位置由 `AppPaths` 决定：**EXE 同目录优先**（便携）；真写一个临时文件探测目录可写性，不可写（如放在 Program Files）→ 回落到 `%AppData%\SelfSwitch\`，并：
  - 托盘气泡告知"配置位置已调整"；
  - EXE 目录里的旧 `config.json` 自动复制到新目录，避免"配置突然变默认"。
- `Load()`：文件不存在 → 生成默认配置；解析失败 → 旧文件备份为 `config.json.bad`，回退默认值，**绝不因为配置坏了打不开程序**。
- `Normalize()`：透明度 0.3~1.0、偏移 -1000~2000、字号 8~48、路径去引号去空格、枚举越界回默认；`OffsetX/OffsetY` 缺省时用旧字段 `EdgeMargin` 代入（老配置平滑升级）。

### 6. 开机自启（两种方式）

| 方式 | 适用 | 权限 |
|---|---|---|
| 注册表 `HKCU\...\Run`（默认） | 目标程序普通权限运行时 | 普通权限即可，**不弹 UAC** |
| 计划任务（`自启-任务计划程序-安装.bat`） | 目标程序必须以管理员运行时 | 创建任务需一次 UAC，之后**登录静默提权启动** |

- 注册表方式：每次启动按当前配置同步——开着就写（值不等于当前 EXE 路径就重写）、关着就删。**EXE 移动后路径自动纠正**。
- 计划任务方式：`New-ScheduledTaskTrigger -AtLogOn` + `-RunLevel Highest` + `LogonType Interactive`。用它时请在配置界面取消勾选「开机自启」，避免双启动（有单实例保护，不会重复运行，只是多一次进程启动）。

### 7. 权限

- manifest 用 `requestedExecutionLevel level="asInvoker"`，日常不弹 UAC。
- 启动检测：对配置的两个 EXE 按进程名找进程并 `OpenProcess`，**返回 ERROR_ACCESS_DENIED（5）**说明对方权限更高且我们控制不了 → 托盘气泡提示"请以管理员身份运行"。
- 需要每次都提权：把 manifest 里 `asInvoker` 改成 `requireAdministrator` 重新编译。
- Windows 的 UIPI 是硬限制：普通权限进程**无法**给管理员进程发键（F11/Alt+Enter 静默失败）也**无法** SetForegroundWindow 它的窗口，这不是本工具能绕过的。

### 8. 稳健性

- 全局异常兜底三处：`DispatcherUnhandledException`（`Handled=true` 不闪退，只弹气泡）、`AppDomain.UnhandledException`、`TaskScheduler.UnobservedTaskException`。
- 所有 Win32 调用失败都写日志（含 `Marshal.GetLastWin32Error()`），不抛给用户。
- 托盘气泡**同一错误 5 秒内去重**（"标题|内容"作 key）。
- 单实例 Mutex：重复双击 EXE 不会出现两个悬浮按钮。
- `Monitor.TryEnter` 防重入：连点按钮时上一次没结束就忽略本次。
- 日志超过 2MB 自动轮转 `app.old.log`；写日志自身异常全部吞掉。

| 最小化旧窗口 | 先 `HWND_NOTOPMOST` 再 `ShowWindow(SW_MINIMIZE)` |
| 覆盖任务栏 | `SetWindowPos(HWND_TOPMOST, 0,0,W,H, SWP_SHOWWINDOW \| SWP_NOOWNERZORDER)` |
| Chrome F11 全屏 | 聚焦 → 判断是否已全屏 → `keybd_event(VK_F11)` → 回检 → 回退 |

## 五、已知限制（客观限制，非 bug）

1. **不能控制管理员权限的窗口**（UIPI 硬限制）——要么提权运行本工具，要么让目标程序不以管理员运行。
2. **F11 / Alt+Enter 依赖目标程序自身支持**——不支持时已自动回退 Win32；个别 DirectX 独占全屏的程序对 `SetWindowPos` 也不买账。
3. 同一程序有多个顶层窗口时，只操作 Z 序最前（或标题关键字命中）的那一个。
4. 切换动作在 UI 线程同步执行（发键后要等回检），单次 0~700ms，这期间的点击被防重入逻辑忽略——刻意设计。
5. 悬浮按钮默认贴主屏**工作区**右下角（任务栏上方）；想压到任务栏上或挪开第三方浮窗，用「锚点 + X/Y 偏移」（负偏移可越过工作区，夹取范围放宽到整屏），原因见 三.4。
6. 本工程已完成编译与单文件发布验证（**0 警告 0 错误**），并已按 v1.4 的测试报告修复全部问题（见 三.4.3）；**窗口切换行为仍需在 Windows 上实测**，实测看 `app.log`（尤其"F11 判断"那两行）。
